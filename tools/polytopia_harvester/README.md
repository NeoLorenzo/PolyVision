# PolyVision Polytopia Map Harvester

## Purpose

This Windows-only utility harvests raw `.state` saves from maps generated by the actual Polytopia desktop game. It uses calibrated screen coordinates to create Bardur Creative games, detects the resulting save through the filesystem, safely copies each unique save into a resumable offline dataset, exits to the menu, and repeats.

It does not parse or convert `.state` files into PolyVision CSV maps. Harvesting and future conversion are deliberately separate tools. It also does not modify Polytopia's live save: the source is only opened for reading and copied.

## Requirements

- Windows and the desktop version of Polytopia;
- Python 3.10 or newer (developed with Python 3.11);
- a stable game-window position, resolution, display scaling, and UI scale;
- PyAutoGUI.

Install the one direct dependency from the repository root:

```powershell
python -m pip install -r tools/polytopia_harvester/requirements.txt
```

PyAutoGUI may install its small Windows input/screenshot dependencies automatically. This harvester does not use screenshots, OCR, template matching, OpenCV, or computer vision.

## Save-directory discovery

The tool searches recursively below:

```text
%USERPROFILE%\AppData\LocalLow\Midjiwan\Polytopia
```

If exactly one `Singleplayer` directory exists, it is selected automatically. If several exist, the tool lists them for selection. If none exist, it asks for the path. An explicit path always wins:

```powershell
python tools/polytopia_harvester/harvest.py --count 10 --save-dir "C:\...\Data\Singleplayer"
```

The selected directory is retained in the local calibration file.

## Calibration

Open Polytopia and make all eight buttons reachable during the guided process, then run:

```powershell
python tools/polytopia_harvester/harvest.py --calibrate
```

For each required button, move the mouse over its centre and press Enter in the console when prompted:

1. New Game
2. Creative
3. Bardur
4. Pick
5. Start Game
6. OK
7. Settings
8. Exit To Menu

The tool captures the current pointer coordinates and screen resolution in `tools/polytopia_harvester/harvester_config.json`. This file is local and ignored by Git. `--calibrate` overwrites all captured coordinates. A harvest automatically enters calibration if no valid configuration exists.

Because pressing Enter focuses the terminal, you can switch between Polytopia and the terminal while collecting each coordinate. Calibration itself never clicks the game.

## Usage

First ten-map harvest:

```powershell
python tools/polytopia_harvester/harvest.py --count 10 --calibrate
```

Later harvest to a total of 10,000 maps:

```powershell
python tools/polytopia_harvester/harvest.py --count 10000
```

Preview the resolved configuration and exact sequence without clicking or writing saves:

```powershell
python tools/polytopia_harvester/harvest.py --count 10000 --dry-run
```

Other supported options:

```text
--save-dir PATH
--output-dir PATH
--config PATH
--verbose
```

`--count` is the desired total dataset size. It is not the number of additional maps to create.

## Startup safety and foreground check

Before sending any click, the tool prints the target, existing and remaining counts, paths, calibrated resolution, historical timing estimate, and safety instructions. It waits for Enter and then counts down for three seconds. During that countdown, click or Alt+Tab to Polytopia. The script checks the foreground window title after the countdown and stops without clicking if it does not appear to contain `Polytopia`.

The current screen resolution must exactly match calibration. A mismatch stops the run and requires `--calibrate`.

While harvesting:

- keep Polytopia at the same position and size;
- do not change resolution, display scaling, or UI scale;
- do not use the mouse or keyboard;
- keep Polytopia foregrounded;
- prevent Windows from sleeping, locking, or displaying notifications over the controls.

## Exact cycle

Every cycle uses this fixed progression:

```text
New Game
-> Creative
-> Bardur
-> Pick
-> snapshot the save directory
-> Start Game
-> OK
-> detect and stabilize the changed .state
-> copy and verify the raw save
-> Settings
-> Exit To Menu
```

Fixed delays are used only for known UI transitions. Save extraction never depends on a fixed sleep alone.

## Save detection and stability

Immediately before Start Game, the watcher snapshots every `.state` filename, size, nanosecond modification time, and filesystem identity available to Python. After OK, it polls until it sees either a new `.state` or a changed existing file. This supports Polytopia reusing the same filename.

The selected file must then keep the same size and modification time, remain non-empty, and be successfully readable for the configured stability duration. A timeout stops the harvester because its screen state can no longer be trusted.

Timing and timeout values are stored in `harvester_config.json` and can be edited between runs:

```json
{
  "click_delays": {
    "new_game": 0.005,
    "creative": 0.005,
    "bardur": 0.25,
    "pick": 0.005,
    "start_game": 3.5,
    "ok": 0.005,
    "settings": 0.005,
    "exit_to_menu": 0.005
  },
  "timing": {
    "poll_interval": 0.1,
    "file_stability_seconds": 0.75,
    "save_timeout_seconds": 20.0,
    "max_duplicate_retries": 3
  }
}
```

Every `click_delays` value is the wait **after** that named click before the next operation. For example, `bardur` controls how long the harvester waits for the Pick option to become ready, while `start_game` controls how long it waits for the OK dialog. The current Start Game delay is exactly 3.5 seconds, matching the observed dialog appearance time without an additional margin.

The final supervised profile uses 0.005 seconds for transitions that proved effectively immediate, 0.25 seconds after Bardur so Pick is ready, and 3.5 seconds after Start Game so OK is visible. PyAutoGUI also applies its separate 0.05-second pause after each call, so a configured 0.005-second delay is not the entire real interval between clicks.

Edit individual values in the local JSON to tune a specific transition without slowing every other click. These values prioritize throughput and must be tested under supervision; increase the preceding button's delay if the following control is not yet ready.

## Output, integrity, and duplicates

The default dataset is ignored by Git and stored at:

```text
data/polytopia_maps/
|-- raw_states/
|   |-- map_000001.state
|   `-- ...
|-- harvest_manifest.csv
`-- harvester.log
```

The source is copied with metadata to a temporary `.partial` file. The tool verifies that:

- the destination exists and is non-empty;
- its SHA-256 matches the stable source;
- the source SHA-256 did not change during the copy.

Only then is the temporary file atomically renamed to its final sequential name. Existing final files are never overwritten. A manifest row is flushed and synced to disk after every success. It includes index, filename, timestamp, cycle time, size, source filename, SHA-256, and source modification timestamp.

An exact SHA-256 match with an existing raw save is considered a duplicate. It is logged, does not increment the successful map count, and triggers a new game cycle. Repeated duplicates are bounded by the configured retry limit, after which the script stops instead of clicking forever. Similar maps with different raw bytes are not rejected.

## Resume behavior and ETA

At startup, the tool counts existing `map_*.state` files and resumes after the highest existing sequential index. For example, if 4,382 maps exist and `--count 10000` is supplied, it reports 5,618 remaining and starts with `map_004383.state`.

The manifest supplies successful cycle times for the initial estimate. Both the startup estimate and live console ETA use only the most recent 10 successful map cycles, so older calibration and slower provisional timings stop distorting the current estimate. Before timing data exists, runtime is reported as unknown rather than guessed.

## Emergency stop

- Move the mouse to the upper-left corner to trigger PyAutoGUI's emergency failsafe.
- Press Ctrl+C for a graceful interruption.

Already completed raw files and manifest rows are retained. The manifest is written and flushed per map, so no separate checkpoint database is required. After any error, manually restore Polytopia to the main menu before resuming.

## Automated tests

The unit tests do not control a desktop or require Polytopia:

```powershell
python -m unittest discover -s tools/polytopia_harvester/tests -v
```

They cover naming, resume and target calculations, hashing and duplicates, manifest writing, ETA, configuration, resolution guarding, new/modified save detection, and stability during simulated writes.

## Manual end-to-end validation

### Test 1 - calibration

```powershell
python tools/polytopia_harvester/harvest.py --calibrate
```

Verify that all eight coordinates and the correct resolution are stored locally.

### Test 2 - one map

Place Polytopia at the main menu and run:

```powershell
python tools/polytopia_harvester/harvest.py --count 1
```

Verify one Bardur Creative game is created, `map_000001.state` is non-empty, the manifest has one row, and Polytopia returns through Settings -> Exit To Menu.

### Test 3 - small batch

```powershell
python tools/polytopia_harvester/harvest.py --count 10
```

Verify ten unique raw saves and ten manifest rows exist.

### Test 4 - resume

Start a larger target, interrupt it, restore the main menu, and rerun the same command. Verify it continues after the highest existing index and does not overwrite files.

### Test 5 - emergency stop

During a disposable small run, move the pointer to the upper-left corner. Verify the process stops and previously completed saves and manifest rows remain valid.

Do not begin an overnight run until all five checks pass on the exact window position, resolution, display scaling, and UI scale that will be used unattended.
